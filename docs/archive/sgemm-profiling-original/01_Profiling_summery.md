####  第一步：看时间 (Duration) —— 找出“罪魁祸首”
在 kernel 列表中，第一眼应该关注的是 **Duration（执行时间）**。
- **做法：** 点击 Duration 表头进行降序排列。
- **原因：** 优化一个只占总运行时间 1% 的 kernel 是没有意义的。需要找到耗时最长的那几个 kernel（我们通常称之为 Top Hot spots），把精力集中在它们身上
#### 第二步：看 SOL 占比 (SM % vs Memory %) —— 定位瓶颈类型

这是 Summary 页面**最重要**的两个指标。NCU 引入了一个概念叫 **Speed of Light (SOL)**，即“光速”。它代表了你当前显卡硬件的**理论性能极限**。这里的百分比，就是你的 kernel 跑到了硬件极限的百分之多少。

需要对比 **Compute (SM) [%]** (计算吞吐/SM利用率)和 **Memory [%]** (显存吞吐和带宽利用率)的数值：
- **情况 A：高 Memory % (例如 > 80%)，低 SM %**
    - **结论：** **内存受限 (Memory Bound)**。你的计算单元在经常“饿着肚子”等数据传过来。
    - **下一步：** 优化方向是全局内存合并访问 (Coalesced access)、使用 Shared Memory 减少全局内存读写、或者优化缓存命中率。
- **情况 B：高 SM % (例如 > 80%)，低 Memory %**
    - **结论：** **算力受限 (Compute Bound)**。你的数据传输很快，但计算单元已经满负荷运转了（都在疯狂做算术题）。
    - **下一步：** 优化方向是减少指令数量（比如用快速数学库 `--use_fast_math`）、减少循环内的冗余计算、或者避免分支发散 (Branch Divergence)。
- **情况 C：两个都很低 (例如都在 20%~40%)**
    - **结论：** **延迟受限 (Latency Bound)** 或者是配置严重不合理。硬件既没在拼命计算，也没在拼命搬砖，都在“发呆”。
    - **下一步：** 通常是因为线程数不够（Occupancy太低，无法掩盖延迟）、指令依赖性太强、或者有严重的同步等待 (Barrier 等待)。
    - 带宽和SM 利用率太低的原因分析：
		* 1 . block的线程太少，每个SM 上同时驻留的block数量是有限的，导致active的warp数量太少，occupency 太低
		* 2. 硬件的资源限制:
			*  每个线程的线程分配的寄存器太多，而每个SM 的寄存器数量是有限的(通常32bit 的寄存器的数量是65536个)，导致同时active的warp数量较少。
			* 共享内存限制：每个block使用的shared memory太多，导致同时驻留的block数量太少。
		* 3.  grid的数量太少，如果grid的数量太少，导致有很多的SM 都在空闲着
		* 4. 即使 Occupancy 看起来还可以，如果指令流无法持续，利用率也会很低。
			* 数据依赖 (Read-after-Write Dependencies): 如果下一条指令必须等待上一条指令的结果（例如高延迟的浮点计算或内存加载），而此时没有足够的其他 Warp 来切入执行，SM 就会陷入 Stall（停顿）。
			* 内存访问延迟 (Memory Latency): 如果存在大量非对齐访问（Uncoalesced Access）或频繁触发 Cache Miss，线程会长时间等待数据从显存（DRAM）返回。由于带宽利用率也低，说明问题可能不在于数据量大，而在于访问太散乱，导致硬件一直在等待寻址。
#### 第三步：看寄存器与配置 (Registers / Block Size) —— 检查基础参数

Summary 里还会列出你的启动配置：
- **Registers Per Thread (每个线程的寄存器数)：** 如果这个数值极高（例如 > 100），会导致一个 Streaming Multiprocessor (SM) 上能同时驻留的线程块变少，从而降低 Occupancy（占用率）。
- **Block Size (Grid, Block 维度)：** 检查你设置的 Block 大小是不是 32 的整数倍（通常推荐 128, 256 等）。如果是奇奇怪怪的数字，会浪费 Warp 的计算资源。

## occupancy 
![alt text](../../profiling/assets/occupancy.png)

**Thread Coarsening（线程粗粒化）** 是一种常见的性能优化策略。它的核心思想是：**让一个线程承担原本由多个线程完成的工作量。**

通常 CUDA 编程鼓励“细粒度并行”（每一个数据项对应一个线程），但在实际硬件架构下，这种极致的拆分并不总是最优的。以下是使用 Thread Coarsening 的主要目的：

### 1. 减少冗余计算和内存访问 (Reduce Redundant Work)

在许多算法（如卷积、矩阵乘法或 Stencil 计算）中，相邻的线程往往需要加载相同的内存数据，或者执行重复的索引计算。

- **目的**：通过让一个线程处理多个连续的输出点，可以将这些共用的数据缓存在寄存器中，从而减少对全局内存或共享内存的访问次数。
- **效果**：降低了带宽压力，节省了指令开销。

### 2. 提高寄存器利用率与数据复用 (Data Reuse)

这是 Thread Coarsening 最直接的好处。

- **目的**：寄存器是 GPU 中访问速度最快的存储空间。通过粗粒化，线程可以将一部分中间结果保存在寄存器中反复使用。
- **例子**：在矩阵乘法 (GEMM) 中，如果一个线程计算一个 $4 \times 4$ 的子块，它只需要加载一次行和列的数据，就可以完成 16 次乘加运算。

### 3. 改善计算密度 (Arithmetic Intensity)

GPU 的计算能力通常远高于其内存带宽（Memory-Bound）。
- **目的**：通过合并任务，减少了为了启动线程而产生的指令开销（如计算 `threadIdx` 的偏移量、边界判定等），同时增加了每个线程内部的计算逻辑。
- **效果**：使程序从内存受限（Memory-bound）向计算受限（Compute-bound）偏移，更好地填满算力。

### 4. 调节并行度与资源平衡 (Resource Scaling)

虽然 GPU 喜欢成千上万的线程，但过多的线程会导致资源争抢。
- **控制占有率 (Occupancy)**：每个线程块（Block）消耗的寄存器和共享内存是有限的。如果线程分得太细，每个线程都要占用基础资源，可能导致硬件无法调度足够多的活跃 Warp。
- **隐藏延迟**：Thread Coarsening 可以手动控制循环展开（Loop Unrolling），利用指令级并行（ILP）来隐藏内存读取的延迟，而不仅仅依赖于硬件的线程切换
